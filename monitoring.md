# 1. Introduction to Observability

## What is Observability?

Observability is the ability to understand what is happening inside a system by examining the information it produces.

Imagine you deploy an application to a server.

Your users begin complaining that the application is slow.

As a DevOps engineer, you need to answer several questions:

- Is the server running out of CPU?
- Is the application consuming too much memory?
- Is the database responding slowly?
- Are users receiving HTTP 500 errors?
- Which API endpoint is taking too long?
- What happened before the application failed?

Without observability, troubleshooting becomes guesswork.

With observability, we can investigate problems using actual measurements and application events.

## Monitoring vs. Observability

**Monitoring** helps us identify when something is wrong.

**Observability** helps us understand why something is wrong.

For example:

Monitoring tells us:

> CPU utilization has reached 95%.

Observability helps us investigate:

> Which processes are consuming CPU, what requests are being processed, and whether users are experiencing errors?

Monitoring is an important part of observability.

# 2. The Three Pillars of Observability

The three traditional pillars are:

1. Metrics
2. Logs
3. Traces

Each provides a different view of our application.

## 2.1 Metrics — What is happening?

Metrics are numerical measurements collected over time.

Examples include:

- CPU utilization: 85%
- Memory utilization: 65%
- Disk utilization: 40%
- HTTP requests per second: 120
- Average response time: 250 milliseconds

Metrics help us understand system performance and identify unusual behavior.

### Example

Suppose our Ubuntu server normally uses 10% CPU.

Suddenly, CPU usage increases to 95%.

Prometheus records the increase, and Grafana displays it on a graph.

We can immediately see that something has changed.

### Tools used

**Node Exporter**

Collects Linux host metrics such as:

- CPU utilization
- Available memory
- Disk space
- Disk read/write activity
- Network traffic

**Prometheus**

Periodically collects metrics from Node Exporter and stores them as time-series data.

**Grafana**

Displays the metrics using dashboards, graphs, and gauges.

### Metrics workflow

```text
Ubuntu Server
     |
     v
Node Exporter
     |
     v
Prometheus
     |
     v
Grafana Dashboard
```

---

## 2.2 Logs — What happened?

Logs are records of events generated by applications, operating systems, and services.

Examples:

```text
INFO: Application started successfully

GET /health HTTP/1.1 200 OK

ERROR: Database connection failed

POST /api/v1/tasks HTTP/1.1 500
```

Logs help engineers investigate errors and understand application behavior.

### Example

Imagine your FastAPI application suddenly stops working.

You execute:

```bash
docker compose logs backend
```

The output shows:

```text
NameError: name 'app' is not defined
```

This tells us that the application is referencing a Python variable before it has been created.

In our practical, we encountered this exact problem when we added the FastAPI monitoring middleware before defining the application.

We corrected it by moving:

```python
app = FastAPI()
```

above the middleware declaration.

### Tools used

**Docker Logs**

Docker captures application output written to stdout and stderr.

**Grafana Alloy**

Collects logs from Docker containers and forwards them to Loki.

**Grafana Loki**

Stores logs and allows them to be searched using LogQL.

**Grafana**

Provides an interface for searching and investigating logs.

### Logging workflow

```text
FastAPI / MySQL / Nginx
          |
          v
      Docker Logs
          |
          v
     Grafana Alloy
          |
          v
      Grafana Loki
          |
          v
    Grafana Explore
```

## 2.3 Tracing — Where did the request spend time?

Tracing helps us understand the journey of a request through an application.

Consider an application where a user creates a task.

The request might follow this path:

```text
User
 |
 v
React Frontend
 |
 v
FastAPI Backend
 |
 v
MySQL Database
 |
 v
FastAPI Response
 |
 v
User
```

A distributed trace can show how long each operation takes.

For example:

```text
Total request duration: 800ms

Frontend/API network: 100ms
Backend processing:   200ms
Database query:       500ms
```

This helps identify bottlenecks.

### Important distinction

In this beginner practical, we did **not** implement full distributed tracing.

Instead, we added a simple FastAPI middleware that records HTTP request duration.

This introduces the idea of measuring request execution time.

For full distributed tracing, we would later introduce tools such as:

- OpenTelemetry
- Grafana Tempo
- Jaeger

These tools support trace IDs, spans, and request correlation across multiple services.

# 6. Configure Prometheus

Create the configuration file:

```bash
nano prometheus/prometheus.yml
```

Add:

```yaml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["prometheus:9090"]

  - job_name: "ubuntu-server"
    static_configs:
      - targets: ["node-exporter:9100"]
```

### Explanation

`global.scrape_interval`

Defines how frequently Prometheus collects metrics.

```yaml
scrape_interval: 15s
```

Prometheus requests new measurements every 15 seconds.

`job_name`

Identifies the monitored service.

`targets`

Specifies the service address and port.

For example:

```text
node-exporter:9100
```

Docker Compose allows containers on the same default network to communicate using service names.

# 7. Configure Loki

Create:

```bash
nano loki/loki-config.yaml
```

Add:

```yaml
auth_enabled: false

server:
  http_listen_port: 3100

common:
  path_prefix: /tmp/loki
  replication_factor: 1
  ring:
    kvstore:
      store: inmemory

schema_config:
  configs:
    - from: "2024-01-01"
      store: tsdb
      object_store: filesystem
      schema: v13
      index:
        prefix: index_
        period: 24h

storage_config:
  filesystem:
    directory: /tmp/loki/chunks
```

### Explanation

Loki listens on port `3100`.

For our lab, Loki stores logs locally using its filesystem backend.

This is a simple single-server configuration, not a production-ready highly available logging system.

Because the example uses container-local temporary storage, logs may be lost when the container is recreated.

# 8. Configure Grafana Alloy

Create:

```bash
nano alloy/config.alloy
```

Add:

```alloy
discovery.docker "containers" {
  host = "unix:///var/run/docker.sock"
}

discovery.relabel "containers" {
  targets = discovery.docker.containers.targets

  rule {
    source_labels = ["__meta_docker_container_name"]
    target_label = "container"
    regex = "/(.*)"
  }
}

loki.source.docker "containers" {
  host = "unix:///var/run/docker.sock"
  targets = discovery.relabel.containers.output
  forward_to = [loki.write.default.receiver]
}

loki.write "default" {
  endpoint {
    url = "http://loki:3100/loki/api/v1/push"
  }
}
```

### Explanation

Alloy performs three important tasks:

1. Discovers Docker containers.
2. Collects their logs.
3. Sends those logs to Loki.

The Docker socket allows Alloy to discover containers and read their logs.

**Security note:** Docker socket access is sensitive and should only be granted to trusted services.

# 9. Add Monitoring Services to Docker Compose

Open:

```bash
nano docker-compose.yml
```

Keep the existing frontend, backend, and MySQL services.

Add the following services under the existing `services:` section.

Do not create another `services:` key.

```yaml
  prometheus:
    image: prom/prometheus:v3.5.0
    container_name: task-manager-prometheus
    ports:
      - "127.0.0.1:9090:9090"
    volumes:
      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - prometheus_data:/prometheus
    restart: unless-stopped

  node-exporter:
    image: prom/node-exporter:v1.9.1
    container_name: task-manager-node-exporter
    command:
      - --path.procfs=/host/proc
      - --path.sysfs=/host/sys
      - --path.rootfs=/rootfs
    volumes:
      - /proc:/host/proc:ro
      - /sys:/host/sys:ro
      - /:/rootfs:ro,rslave
    pid: host
    restart: unless-stopped

  loki:
    image: grafana/loki:3.5.3
    container_name: task-manager-loki
    command: -config.file=/etc/loki/local-config.yaml
    volumes:
      - ./loki/loki-config.yaml:/etc/loki/local-config.yaml:ro
    restart: unless-stopped

  alloy:
    image: grafana/alloy:v1.10.2
    container_name: task-manager-alloy
    command:
      - run
      - /etc/alloy/config.alloy
    volumes:
      - ./alloy/config.alloy:/etc/alloy/config.alloy:ro
      - /var/run/docker.sock:/var/run/docker.sock:ro
    depends_on:
      - loki
    restart: unless-stopped

  grafana:
    image: grafana/grafana:12.1.0
    container_name: task-manager-grafana
    ports:
      - "127.0.0.1:3001:3000"
    environment:
      - GF_SECURITY_ADMIN_USER=admin
      - GF_SECURITY_ADMIN_PASSWORD=${GRAFANA_ADMIN_PASSWORD}
    volumes:
      - grafana_data:/var/lib/grafana
    depends_on:
      - prometheus
      - loki
    restart: unless-stopped
```

At the bottom of the Compose file, ensure the existing volumes section includes:

```yaml
volumes:
  mysql_data:
  prometheus_data:
  grafana_data:
```

Create or update the root `.env` file:

```dotenv
GRAFANA_ADMIN_PASSWORD=REPLACE_WITH_A_STRONG_PASSWORD
```

Keep passwords out of Git.

### Why use Docker volumes?

Docker volumes allow data to survive container recreation.

We use volumes for Prometheus and Grafana data.

**Important:** Do not run `docker compose down -v` because that can delete your existing MySQL database volume.

### Query CPU utilization

```promql
100 * (1 - avg(rate(node_cpu_seconds_total{mode="idle"}[1m])))
```

### Query memory utilization

```promql
100 * (
  1 -
  node_memory_MemAvailable_bytes
  /
  node_memory_MemTotal_bytes
)
```

### Query disk utilization

```promql
100 * (
  1 -
  node_filesystem_avail_bytes{mountpoint="/",fstype!~"tmpfs|overlay"}
  /
  node_filesystem_size_bytes{mountpoint="/",fstype!~"tmpfs|overlay"}
)
```

### Query disk activity

```promql
sum(
  rate(node_disk_read_bytes_total[1m])
  +
  rate(node_disk_written_bytes_total[1m])
)
```

This last query measures disk throughput in bytes per second, not the percentage of disk space used.

# 15. Practical 1 — CPU Stress Testing

### Objective

Generate CPU load and observe the change in Grafana.

Run:

```bash
stress --cpu 2 --timeout 120s
```

### Explanation

`--cpu 2`

Starts two CPU-intensive workers.

`--timeout 120s`

Stops the test automatically after two minutes.

### What we observed

During our practical:

- CPU utilization increased toward 100%.
- Prometheus collected the increase.
- Grafana displayed the CPU spikes.
- CPU utilization decreased after the test completed.

### Why did CPU reach 100%?

Our server had two logical CPUs.

We launched two CPU workers, allowing the test to heavily utilize both CPUs.

### Understanding averaging windows

We compared two queries.

**One-minute CPU average:**

```promql
100 * (1 - avg(rate(node_cpu_seconds_total{mode="idle"}[1m])))
```

**Five-minute CPU average:**

```promql
100 * (1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])))
```

The one-minute query responded more quickly to CPU changes.

The five-minute query smoothed the results over a longer period.

This explains why one CPU graph reached nearly 100%, while another displayed a lower peak.

# 16. Practical 2 — Memory Stress Testing

### Objective

Generate memory load and observe RAM utilization.

First, check available memory:

```bash
free -h
```

Run:

```bash
stress --vm 1 --vm-bytes 256M --timeout 60s
```

### Explanation

`--vm 1`

Starts one memory worker.

`--vm-bytes 256M`

Allocates approximately 256 MB of memory.

`--timeout 60s`

Stops after one minute.

### What we observed

Our RAM utilization increased from approximately 32% to above 38% during the practical.

Grafana displayed the increase.

For a longer memory test, if the server has sufficient available memory:

```bash
stress --vm 1 --vm-bytes 256M --vm-keep --timeout 120s
```

The `--vm-keep` option helps keep the memory allocation active.

**Safety:** Never allocate more memory than the server can safely spare. Memory pressure can cause application failures or out-of-memory termination.

# 17. Practical 3 — Disk Stress Testing

### Objective

Generate disk activity and observe disk throughput.

Run:

```bash
stress --hdd 1 --hdd-bytes 128M --timeout 30s
```

### Explanation

`--hdd 1`

Starts one disk I/O worker.

`--hdd-bytes 128M`

Sets the amount of data written per worker cycle.

`--timeout 30s`

Stops the test after 30 seconds.

### Grafana query

```promql
sum(
  rate(node_disk_read_bytes_total[1m])
  +
  rate(node_disk_written_bytes_total[1m])
)
```

Set the visualization unit to bytes per second.

### What we observed

Our Grafana dashboard showed disk throughput rising to approximately 7 MB/s.

After the test, throughput dropped toward its previous level.

### Disk usage vs. disk activity

These are different measurements.

**Disk usage** measures how much storage capacity is occupied.

Example:

```text
Disk capacity used: 22.8%
```

**Disk activity** measures how much data is being read or written per second.

Example:

```text
Disk throughput: 7 MB/s
```

During our test, disk activity increased while disk capacity usage remained approximately 22.8%.

This is expected because temporary disk activity does not necessarily increase permanent storage consumption.

# 20. Practical 5 — FastAPI Request Timing

We introduced basic request timing using FastAPI middleware.

Open the file containing your FastAPI application.

In our project, the application was started using:

```text
uvicorn app.main:app
```

Therefore, the middleware was added to the FastAPI application module.

### Example implementation

```python
import time

from fastapi import FastAPI, Request
from fastapi.middleware.cors import CORSMiddleware

from app.api.v1.router import api_router


app = FastAPI(
    title="Task Manager API",
    version="1.0.0",
    redirect_slashes=False
)


app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)


@app.middleware("http")
async def monitor_request(request: Request, call_next):
    start = time.perf_counter()

    response = await call_next(request)

    duration = time.perf_counter() - start

    print(
        f"{request.method} {request.url.path} "
        f"status={response.status_code} "
        f"duration={duration:.3f}s",
        flush=True
    )

    return response


@app.get("/health")
def health_check():
    return {"status": "healthy"}


app.include_router(
    api_router,
    prefix="/api/v1"
)
```

### How the middleware works

1. A request reaches FastAPI.
2. The middleware records the start time.
3. FastAPI processes the request.
4. The middleware calculates the elapsed time.
5. The result is written to the application logs.

### Rebuild the backend

```bash

```

### Generate requests

```bash

```

Run multiple requests:

```bash

  curl -s http://localhost:8000/health
  echo
done
```

### Example output

```text

GET /health status=200 duration=0.002s

GET /health status=200 duration=0.001s
```

### View request timing in Grafana

Open Explore and select Loki.

Run:

```logql

```

During our practical, Grafana successfully displayed the request duration logs.

### Important lesson

This is basic request timing, not distributed tracing.

It measures the total time spent processing a request but does not separately measure database queries or downstream service calls.

# 21. Troubleshooting Issues We Encountered

## Issue 1 — FastAPI NameError

Error:

```text
NameError: name 'app' is not defined
```

### Cause

We attempted to register middleware before creating the FastAPI application.

Incorrect order:

```python
@app.middleware("http")
async def monitor_request(...):
    ...

app = FastAPI()
```

Correct order:

```python
app = FastAPI()

@app.middleware("http")
async def monitor_request(...):
    ...
```

### Lesson

Python executes module-level code in order. Variables must exist before they are referenced.

# 25. Production Considerations

Our configuration was designed for learning.

Before using a similar stack in production, consider:

- Securing Grafana with strong credentials and HTTPS.
- Restricting access to monitoring endpoints.
- Protecting the Docker socket.
- Using persistent storage for Loki.
- Configuring retention policies.
- Adding resource limits and health checks.
- Protecting database credentials.
- Monitoring application availability.
- Configuring alerts for critical conditions.
- Adding distributed tracing with OpenTelemetry.
- Backing up Grafana dashboards and configuration.

Also, avoid publicly exposing MySQL or backend ports unless access is explicitly required and appropriately secured.

# Conclusion

In this practical, we learned how to implement observability for a Docker Compose application running on Ubuntu.

We used Prometheus and Node Exporter to collect infrastructure metrics, Loki and Alloy to centralize Docker logs, and Grafana to visualize our monitoring data.

We also introduced request timing using FastAPI middleware and demonstrated how CPU, RAM, and disk stress tests affect server performance.

The most important lesson is that observability helps DevOps engineers move from guessing about application problems to investigating them using real evidence.

**Logs tell us what happened.**

**Traces help us understand where time is spent across a request's journey.**

Together, they form the foundation of modern application observability.
